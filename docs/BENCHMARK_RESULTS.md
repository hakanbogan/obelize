The two derived codes are consequences, not causes.
`file_not_fully_migrated` is a ready row in a file that was not;
`repo_not_fully_migrated` is a legacy pin kept until the code importing it is
gone. Both are atomicity working as
[the fixture rules](adr/ADR-010-fixture-oracle-and-atomicity.md) say it should.

`generation_config_not_static` ties for the largest lever, against a written
prediction. Every instance is a name assigned once and readable: a
module-level `genai.GenerationConfig(...)`, a module-level dict literal, a local
built two statements above the call. Tracing this bail
through the three-repository development corpus found it bought no edit;
that corpus under-represented the commonest way to write a generation config.

`multiple_configure_calls` is worth nothing on its own, because every file
it touches also carries `local_import`. Ranked by count it would come second.

One `alias_collision` is all that stands between
`Omadithya07/Phidata-Multimodal-Video-Summarizer-Using-AI-Agents` and a
complete migration. `from google.generativeai import upload_file,get_file`
on line 5 and `import google.generativeai as genai` on line 6: rewriting the
first asks for the alias the second already binds.

One lever must not be taken. `history_parts_shape_incompatible` is two
lines, in two near-identical copies of one file, reading
`model.start_chat(history=str(time.time()))`: a float rendered as a string,
which is not a history in either SDK. A rule that rewrote it would migrate a
defect, which is why the lever column carries a disposition, not a ranking.

Three causes are one wall. `module_returned_from_function`,
`star_import_binding` and `module_from_subscript` are the legacy module bound
to a name through a function return, a star import in another file or a
container subscript, and the resolver follows none of the three. That, not any
rewrite rule, is where the round's recall went.

Lifting every bail would not move the headline. It would complete twelve of
the twenty repositories, but ten of those have no test command, one has a
`manual` row and one a line the pack flags, so all twelve stay capped below
`verified_success`.

One key row was wrong, and correcting it moved no published number; see
[`bench/CASES.md`](../bench/CASES.md#how-the-ground-truth-was-written).

The agent cleared about seven times as many rows, about forty-five times
slower.

Both of its `wrong` cases are real defects, and a suite caught one. In
`humanbound/humanbound-firewall`, whose suite covers the change,
`_import_genai()` exists to turn a missing optional dependency into
an `ImportError` naming the `[gemini]` extra. `from google import genai` does
not raise there, because `google` is a namespace package, so the user gets
`AttributeError: 'NoneType' object has no attribute 'Client'` and a test fails,
although the agent also rewrote both test modules, including the lazy-import
guard's `FORBIDDEN_MODULES`. In `Arnav3241/Jarvis-v13` it took the lever the
error analysis above says must not be taken, turning
`start_chat(history=str(time.time()))` into
`client.chats.create(history=[types.Content(role='user',
parts=[types.Part(text=str(time.time()))])])`: a user turn invented from a
Unix timestamp.

The agent's account of its work was wrong on the largest case. Its report
for `Arnav3241/Jarvis-v13` says a repository-wide grep finds no legacy
reference. `Tests/r1.py` has five, which neither run touched, and they are the
whole gap between the rows the scanner sees there and the rows the agent
cleared. Only the answer key shows it.

Comparing the arms exposed a scanner defect. Round 1 matches rows on
`(path, line, symbol)`, so key and scanner never had to agree on kind. In
`humanbound/humanbound-firewall` the key grades six `sys.modules` stubs
`dynamic` and the scanner reports them as `text_mention`, which is
`not_a_usage`: a repository whose tests mock the legacy module has those lines
left behind silently, and `tests_touched_by_migration` never fires. The agent
had to rewrite all six. `COVERAGE.md` gap 34.

The agent is not repeatable. Its re-runs touched the same files and
cleared the same rows with different line counts, and on
`Arnav3241/Jarvis-v13` the first run turned a line into a fabricated turn and
the second deleted it, which keeps behaviour: same input, same score, opposite
judgement about a defect.

The ceiling caps a rule, not a tool. On `LucasHJin/vit` the agent migrated
all eight `manual` rows and the project's hundred tests pass, so it reached
`verified_success` on a case the ceiling closes to a rule. It did so with an
option the key did not list: an adapter class that *is* a model object,
leaving the six callers and the seven tests that patch that seam untouched. The
review accepted it; whether the abstraction is worth carrying is the
maintainer's call. So the two cases where a suite could speak produced one
verified success and one regression.

Obelize is ahead on what a reviewer must read, not on accuracy: no rejected
edit, no file off the key, no new legacy usage, byte-identical output, and a
`run.json` naming every refused row and why. The agent's off-key edits to
READMEs, a changelog and project documentation were not asked for and are
recorded nowhere a reviewer would see.

Limits. One agent, one day, one guide snapshot, and only the split
obelize's rules were tuned against. The agent ran up to eight cases
concurrently on one machine, so its runtime is an order of magnitude, not a
benchmark. Every free choice favoured the agent.
